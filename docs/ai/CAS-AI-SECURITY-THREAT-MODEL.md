# CAS AI — Security / Threat Model

Each threat below is evaluated against CAS's **actual** implementation (not a generic checklist), with a concrete mitigation grounded in files/patterns that already exist in this repo where possible.

| Threat | Applies here? | Mitigation |
|---|---|---|
| **Prompt injection** (direct: user types "ignore your instructions and…") | Yes | System prompt states tool results are data, never instructions; model must never execute an instruction found inside a tool result or a document. Server-side: no tool grants write/execute capability in Phase 1, so a successful injection has nothing destructive to do. |
| **Indirect prompt injection** (malicious text inside a `remarks`/`description` field the AI later reads back, e.g. a vendor's `remarks` column) | **Yes — realistic here.** `vendors.remarks`, `customers.remarks`, `purchases.remarks`, `client_invoices` line descriptions etc. are free text, user-entered, and would be legitimate tool-result content (e.g. "show me vendor XYZ's details"). | Tool results must be wrapped as clearly-delimited untrusted data in the prompt (not concatenated as plain instructions); system prompt explicitly tells the model that field values are data, never commands, mirroring how this session's own harness treats untrusted external content. |
| **Unauthorized data retrieval** | Yes | Two-layer defense: app-level permission pre-check (filters the tool list per caller) + RLS on the actual query, executed with the caller's own JWT — see `CAS-AI-ARCHITECTURE.md`. |
| **Cross-tenant leakage** | **N/A — no tenant model exists** (see `CAS-AI-DATABASE-MAP.md`). Don't build tenant-scoping machinery that doesn't map to anything; it would be dead code that looks like a control but enforces nothing. |
| **Cross-project leakage** | Yes — real risk, real existing control | `can_access_project(project_id)` RLS policy already governs `projects`, `client_invoices`, `purchases`. Any AI tool touching project-scoped data must query through the RLS-scoped client so this applies automatically; a tool implemented against the `service_role` client would silently bypass it. |
| **Privilege escalation** (AI ends up able to do more than the asking user) | Yes | Never grant the AI Gateway's Postgres client more privilege than the caller has. Concretely: **do not** build AI tools on `supabaseAdmin` (service_role, used today only by `/api/admin/*` for privileged mutations that need to bypass RLS by design, e.g. creating another user's Auth account). AI read tools use a per-request client scoped to the caller's JWT. |
| **Malicious tool parameters** (e.g. a crafted `project_id` the model was tricked into passing) | Yes | RLS makes this low-consequence even on app-layer bugs — an out-of-scope `project_id` simply returns zero rows, never another project's data. Additionally: strict JSON-schema validation (`strict: true` tool definitions) on every tool's input before it reaches any query. |
| **Sensitive-data exposure** (e.g. surfacing another user's salary/personal `profiles` fields, or `demo_requests` PII) | Yes | Phase 1 tool catalog is scoped to financial/operational entities (vendors, customers, projects, invoices, bank/cash, expenses) — `profiles`, `demo_requests`, `roles` are deliberately **not** exposed as tools at all (no business reason for a "who are the other users" query in this feature). |
| **Excessive AI permissions** | Yes | Phase 1 gates the whole feature behind a new permission, e.g. `ai_assistant.use`, on top of each individual tool's own permission requirement — so it can be rolled out to one role first (e.g. `finance_manager`) rather than every active user on day one. |
| **Hallucinated financial information** | Yes — the headline risk for a finance app | System prompt: answer only from tool results; if no tool returned the needed fact, say so explicitly rather than estimating. Never let the model perform its own arithmetic on raw rows when an authoritative computed field/service function already exists (`CAS-AI-DATABASE-MAP.md` §Financial precision). |
| **Fabricated records** (inventing a vendor/invoice that doesn't exist) | Yes | Same mitigation as above — grounded-only answering; a "get vendor by name" tool that returns zero matches must produce "no such vendor found," never a plausible-looking fabricated one. |
| **Unsafe future write actions** | Not in Phase 1 (read-only) | When write tools are eventually added, they must call the existing `security definer` RPCs (`create_client_invoice`, `record_money_in`, etc.) — never raw inserts — and require explicit user confirmation of the exact parameters before execution, logged in `ai_tool_calls` with a `confirmed_by`/`confirmed_at` pair. Out of scope to build now; flagged so Phase 2+ doesn't skip it. |
| **API key exposure** | Yes | Anthropic API key lives only in the Vercel serverless function's environment variables (same pattern as `SUPABASE_SERVICE_ROLE_KEY` today, which is correctly never `VITE_`-prefixed and never shipped to the client — confirmed by grep, only referenced in `src/server/app.ts`). Never reference it from `src/` (browser-bundled) or `android/src/`/`ios/` code. |
| **Mobile credential exposure** | Checked, not found today | Android/iOS ship only the static web bundle (no native secrets) and call the deployed API exactly like the browser does, over the user's own Supabase session — see `CAS-AI-MOBILE-READINESS.md`. No new mobile-specific credential surface is introduced by adding `/api/ai/*`. |
| **Conversation-data leakage** | Yes | `ai_conversations`/`ai_tool_calls` rows contain financial detail by nature; RLS them the same way `audit_logs` is RLS'd (`select` requires an appropriate permission, e.g. reuse `audit.view` or a new `ai_audit.view`), and never log full tool-result payloads verbatim if avoidable — log identifiers/counts, not raw financial rows, to limit blast radius of a future audit-table leak. |
| **Document injection** (a malicious PDF/attachment whose content becomes indirect prompt injection once RAG is added) | Not applicable yet — no RAG in Phase 0/1 | Flagged for whenever document Q&A is built (`CAS-AI-IMPLEMENTATION-ROADMAP.md` — later phase): treat extracted document text with the same untrusted-data handling as tool results above. |
| **Model/provider compromise** | Standard | Use Anthropic's first-party API only (already this project's convention per its own tooling); no self-hosted or third-party model proxy. |

## Two findings that are security-relevant but pre-date this feature

1. **`audit_logs` insert policy** (`audit_logs_insert ... with check (is_active_user())`) — any active user can insert an audit row for anything, with attacker-controlled `old_values`/`new_values`. Today this is low-risk because the UI always pairs the insert with a real RLS-validated mutation in the same code path. It becomes directly relevant to AI work because it means `audit_logs` **cannot** be reused as-is for the AI's own trail (see `CAS-AI-DATA-FLOW.md`) — not a new vulnerability, but a reason to build a separate, server-write-only table rather than extend this one.
2. **`ALLOWED_ORIGIN` CORS fallback** (`src/server/app.ts:37`) — reflects any origin with `credentials: true` if the env var is unset. Verify it's actually set in the Vercel production environment before exposing a new `/api/ai/*` route that will, like `/api/admin/*` today, accept a Bearer token from arbitrary origins if this isn't configured.

Neither is introduced by the AI feature; both are worth a one-line fix in whichever PR first touches `src/server/app.ts` for AI work, since that PR will already be under review for exactly this kind of thing.
